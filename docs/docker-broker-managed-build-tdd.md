# Managed identity Pi image build — test list and evidence

## Scope and behavior list before production

1. Only the explicit host-managed `ManagedDocker` may perform an image build. No ambient `docker` via PATH/context, no Docker executable/socket/config inside Pi, no project Dockerfile, host shell, or arbitrary Docker argv.
2. Build context is a private 0700 host-owned temporary directory outside the caller-supplied canonical host project workspace, containing only `embed::extract_with_identity_to` files and a newly emitted identity Dockerfile. No `.pithos`, credentials, workspace source, environment secret, or Docker config is copied into context. The Dockerfile's base must be bound to the full previously inspected local base image ID; do not rely on a mutable tag between fingerprinting and build.
3. Verify source identity/fingerprint against the exact raw validated config and effective host UID/GID; reject browser-enabled config and unsupported/changed daemon/selection before build. Use the same bounded cache fingerprint contract and label namespace. No implicit registry pull; on cache hit build does nothing.
4. Fixed `docker build --pull=false` argv, `--iidfile` in the private context, bounded supervised local child (longer than 3-second metadata queries), cleared environment, bounded output drainage and cooperative cancellation. Retain child ownership on errors/timeout and do not claim daemon cancellation; never use an uncertain image.
5. Read exactly one full private image ID from a single-link 0600 owned file with no symlinks; inspect the full ID through the same frozen owner after build. Require exact ID, label, numeric identity, Pi env and no Config.Volumes; daemon/base selection must not change. Never retag or adopt a foreign image.
6. Build failures retain the managed Docker owner for explicit child polling; no automatic image deletion/volume creation, cache fallback, home migration or CLI activation. Project toolchain installer labels from legacy two-pass builds remain deferred unless explicitly safely implemented.
7. Fake-Docker real process/FS tests are not proof of native Linux/macOS Dockerfile `FROM` acceptance; keep activation blocked pending real Docker.

## TDD evidence

Implemented the guarded host-owned build slice without activating runtime/main. Test-first: `tests/managed_image_build.rs` was added against a deliberately non-authorizing `ensure_identity_image` stub. The initial Cargo invocation could not write `/opt/cargo` (environment/setup failure, not Red); rerunning with `CARGO_HOME=/tmp/pithos-cargo` and `--offline` produced five compiled tests with four **behavioral assertion failures**: miss returned `Unavailable`, cache hit returned `Unavailable`, unsafe root returned `Unavailable` instead of `InvalidSelection`, and changed-base scenario never built. Full output: `/tmp/pithos-runtime-tdd/image-build/01-red.log`. The production implementation then passed the first Green at `/tmp/pithos-runtime-tdd/image-build/02-green.log` (5/5). Added adversarial cases for before/after base changes, symlink/mode/hardlink iidfile, wrong label, workspace/aliased/unsafe stage, invalid/browser YAML, and cooperative cancellation; Green: `/tmp/pithos-runtime-tdd/image-build/04-green.log` (build 6/6, cache 11/11), followed by `/tmp/pithos-runtime-tdd/image-build/05-green.log` (build 7/7, including failed-CLI retry and malformed ID) and `/tmp/pithos-runtime-tdd/image-build/06-green.log` and `07-green.log` (build 8/8, including truncated but drained build output and exact argv). After moving the pre-build base recheck to immediately after staging, `/tmp/pithos-runtime-tdd/image-build/final-tests.log` passes build 8/8 and cache 11/11. The longer focused suite before those last two cases is at `/tmp/pithos-runtime-tdd/image-build/focused.log` (build 6, cache 11, handoff 5, preflight 23, Pi 22 passed).

The first Red covered cache-hit, cache-miss, base-change build dispatch and unsafe-root behavior; later adversarial checks were added after that Green and are **not** claimed as independent Red cycles. One later private-stage-mode assertion exposed a real failure (tempfile's default tempdir permissions are 0777 masked by umask, not 0700); the builder now requests 0700 at creation and verifies ownership/mode before extraction. Reviewer follow-up (strict test-first): `/tmp/pithos-runtime-tdd/image-build-review/01-parent-red.log` records an assertion failure on a 0700 root beneath an untrusted 0777 parent **even with a cache hit** (returned an image rather than `InvalidSelection`). `/tmp/pithos-runtime-tdd/image-build-review/02-workspace-red.log` records an assertion failure on a 0700 root inside a real project outside the source repository (returned an image). Both Red runs compiled and failed on behavior, not setup. `/tmp/pithos-runtime-tdd/image-build-review/03-green.log` passes 11/11, including alias, unsafe workspace, both directions of overlap and no-query/no-write checks. `ensure_identity_image` now requires a canonical existing host workspace path, checks all ancestors of both workspace and staging root using `symlink_metadata`, allows only root/effective-UID owned directories without group/other write (except root-owned sticky directories *above* the checked directory, e.g. `/tmp`), and requires the staging root itself to be effective-UID-owned 0700. These pathname metadata checks exclude other-UID parent renames under the stated trust model; same-UID/root adversaries and TOCTOU between checks and use are **not** excluded. No fd-based path capability or race-free staging claim is made. The checks also precede cache-hit Docker queries.

The build uses a separately supervised 3600s maximum child with cleared environment and bounded drained output, private staged embedded context, observed base ID in `FROM`, no pull/tag, an existing private iidfile checked with no-follow and nlink/mode/owner bounds, and frozen full-ID metadata queries. Failure never returns an image; a retained build child retains its stage, and dropping an unresolved owner intentionally leaks the stage rather than deleting files under a running child. This does **not** prove daemon-side build cancellation, registry independence of commands inside installer scripts, descendant quiescence, or native Docker acceptance of `FROM sha256:<full id>`; real Docker and Linux/macOS target validation remain activation blockers. Runtime/main remains gated.
