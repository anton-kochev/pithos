# Persistent database-volume registry — behavior list

This is a host-private, **offline** stable stack owner, separate from the per-run probe/Pi manifest. It neither calls Docker nor authorizes creation, adoption, mounting, deletion, or volume replacement. Compose remains unexecutable until typed Docker observations and operations are implemented.

- An exclusive process lock covers a validated project/stack key and private state under a fixed host broker root (outside the workspace); different stacks are independent. A durable active/debt marker persists on drop/crash and only a positive settlement can clear it; conflicting simultaneous owners fail. A marker from a prior run is never cleared or silently adopted by a new run.
- Store a bounded, versioned, private, atomically replaced `volumes.json`; synchronize file and parent. Existing initialized state with missing, corrupt, oversized, symlinked or misowned components fails closed. First initialization is explicit and recoverable, with durable marker and snapshot before any future Docker mutation.
- Persistent mappings are keyed by Compose-validated logical volume names, with immutable selected daemon, generated physical volume name, nonce, labels, and creation fingerprint. A fresh create intent must be durable before a Docker mutation; ambiguous create stays intent and never grants a second create. Confirmation requires an exact, immutable observed identity. Confirmed missing/mismatched identity cannot be mapped to a new or empty volume. Registry has no volume-delete API.
- Same stack across separate runs reopens existing mapping; no automatic migration/repair. Keep per-run resource journal independent. Deny operation when poisoned or active debt remains, and redact user data in errors.

## Review follow-up: duplicate keys, independent stack keys, and lint

`CARGO_HOME=/tmp/pithos-cargo cargo test --offline --test broker_volumes -- --nocapture` compiled and ran 7 tests before the fix: `duplicate_logical_entries_are_corrupt_without_rewrite` failed because a second valid `data` entry replaced the first in the deserialized map, and `locked_stacks_root_does_not_block_other_stack_keys` failed because initialization returned `Busy` while an external handle locked the stacks root. The optional `created_at` duplicate test passed on first execution (characterization: derived struct deserialization already rejects it). The top-level `entries` duplicate test was added afterward and likewise characterizes existing rejection; neither is claimed as a behavioral Red.

A map visitor now rejects repeated logical keys before reading/replacing their values and enforces the entry count while decoding. Per-key exclusive mkdir and the per-stack lease protect initialization and ownership; no lock on the shared root is needed. Initialization still syncs the root immediately after mkdir to make the directory name durable before writing child state. With a controlled external root lock held, initialization of a fresh key and opening a different existing key no longer return `Busy`; active debt still requires recovery. Both new behavioral tests and existing registry tests passed after implementation. `src/broker/state.rs` now places its unit tests at the end for strict Clippy; `cargo fmt --all` applied the previously pending formatting, including `tests/broker_host_state.rs`, without changing behavior. No dependencies or commits were added.

Remaining boundary: intent, confirmation and positive settlement remain test-only until typed daemon verification exists. There is still no Docker operation, reconciliation, automatic recovery, or defense against malicious same-UID replacement of trusted ancestors. These tests assume local Unix filesystem lock and directory sync semantics.
